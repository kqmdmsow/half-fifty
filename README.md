# half-fifty (하프피프티)

**금융 취약계층을 위한 계약 문서 단순화·위험 안내 에이전트** — 2026 전기 졸업과제

> 계약서의 정보 비대칭 때문에, 위험한 조항인 줄 모르고 서명해서 실질 피해를 입는
> 문제를 풉니다. 계약서를 올리면 조항 단위로 **① 위험 판정 ② 눈높이 설명
> ③ 서명 전에 해야 할 확인 행동**을 제시합니다. 판정 근거는 정부·법원이 실제로
> 판단한 사례(골든데이터셋)로 검증합니다.

## 아키텍처

```
프론트(5173) → 백엔드(8080) → 에이전트(8000)
                                └─ Parser → Domain → Analysis → Persona → Judge
                                                        ↑ 점수 미달 시 최대 2회 재실행 ┘
```

Domain은 문서 유형(주택/상가 임대차, 보험, 대출 등)을 1회 판별해 Analysis의
모든 조항 판정에 주입한다 — 같은 문언도 유형에 따라 판정이 갈리기 때문.

```
half-fifty/
├── agent/      # Python + LangGraph 5단계 파이프라인 (담당: 최민제)
├── backend/    # Java Spring Boot API 서버 (담당: 전동훈)
├── frontend/   # React + TypeScript + TailwindCSS (담당: 김민찬)
├── data/       # 골든데이터셋·앵커쌍 (hldcc·LBox·AI Hub·금감원 실측 라벨)
└── docs/       # 실험 리포트, 검증 설계, 회의록
```

- 5단계 파이프라인은 단일 LLM 호출(Baseline) 대비 우위를 실측으로 비교·검증합니다
  (`docs/eval_baseline_vs_ours.md` 계열).
- Judge는 운영 중 품질 게이팅(임계값 미달 시 재시도)과 평가 채점을 담당합니다 —
  아래 "저울 교정" 참조.

### 1. 골든데이터셋 구축 (정부·법원 판정 기반)

| 세트 | 규모 | 내용 |
|---|---|---|
| 공식 Test | 40건 (A등급 27) | hldcc 조정례·LBox 판례·AI Hub — held-out, 개선 확정 시 1회만 측정 |
| 임대차 확장 | 34행 (train 13 / val 3 / test 18) | 경계 안전("위험해 보이나 유효") 포함, 대조쌍 설계 |
| 금융 전이 | 33행 (train 9 / val 5 / test 19) | 보험·대출·카드·금투 — 도메인 전이 검증용 |
| 정답앵커 쌍 | 40쌍 | Judge 신뢰도 검증(RQ6) 전용 |

- 수집 파이프라인: 키워드 필터 → 판결문·결정서 원문 정독(라벨링 에이전트) →
  **독립 적대적 검수**(별도 에이전트가 원문 재대조·반박 시도) → 통과분만 반영.
  3라운드 누적 제안 ~100건 중 검수 통과율 약 55~60% — 기각 사유는 전부 문서화.
- 오염 방지 원칙: train/val은 자유 반복(프롬프트 튜닝용), **Test는 절대 보지 않고
  개선 확정 시 1회만** 실행. 같은 사건은 같은 split(누수 차단).

### 2. 저울 교정 — LLM Judge를 믿어도 되는가 (RQ6)

"프롬프트를 고쳤더니 좋아졌다"를 말하려면 채점자(LLM Judge)부터 검증해야 합니다.

- **4개 모델 패밀리 판사**(Claude·Gemini·Solar·DeepSeek)에게 정답앵커 40쌍을
  동일 프로토콜(위치편향 통제 2회×3회 반복 다수결)로 채점시킨 결과, **패널 다수결
  기준 clarity/risk_coverage/actionability 100%, faithfulness 97%** —
  `docs/eval_pairwise_judge_family_round2.md`
- 과정에서 앵커쌍 제작 결함(라벨 메모 노출)을 발견해 전면 재작성했고, worker와
  같은 패밀리 판사의 self-preference 우려를 교차검증으로 완화했습니다.
- 방법론 발견: 판정 편중에 의한 κ-역설 → 사람-LLM 일치 분석은 Gwet's AC1
  병기 권고.

### 3. 성능 실측과 개선 사이클

- **공식 확정 수치(2026-08-25, #174 6층 인젝션 방화벽 프롬프트 반영 재측정)**:
  공식 Test 40 **전체 입력 기준 Acc 72.5%(29/40)** · P0.71/R0.87/F1 0.78. 확장
  세트(3회 반복 다수결, 도메인 전이 실험): ext 18건 Acc0.61(P0.54/R0.88),
  finance 라벨 확정 16건 Acc0.75/R1.00(P0.43) — 2건은 텍스트가 원 조항이
  아니라 분쟁조정 판정문 재구성·부분인용이라 라벨 품질 보류(집계 제외,
  CSV note에 사전 표시된 결함) — `docs/eval_ext_sets_pr174_repeats3.md`.
  수치의 단일 출처는 **`docs/공식수치.md`** (이슈 #56)
- 위험 유형 6→10종 확장(v2.1)·도메인 라우팅·citation_check 반복 수정을 거치며
  수치가 여러 차례 움직였다(0.72→0.78→0.72→최종 0.70). 매 변경마다 FP를
  개별 대조해 코드 회귀인지 표본 변동인지 구분하고 정직하게 기록했다 — 최종
  하락분(0.72→0.70) 원인 2건은 로컬 대조로 citation_check와 무관함을 확인
  (경계 케이스 변동성 1건, 조항 단위 평가의 구조적 한계 1건) — 이슈 #56 코멘트.
- 오탐 공략 튜닝 라운드 1: train/val 53%→88%. `docs/eval_fp_tuning_round1.md`
- 평가 인프라: 쌍 단위 체크포인트(중단 안전), 반복 다수결(재현성), 평가 실행
  병렬화·프롬프트 캐싱(PR #20).
