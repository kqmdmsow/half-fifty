# 조항 단위 표본 증식 + Train/Val/Test 분리안

> 2026-07-25 교수님 중간 상담 피드백(실험진행도 B — "데이터·검증 부족") 대응 1단계.
> 산출물: `data/clause_level_labels.csv` (66개 조항 라벨, 재실행 없이 기존 자산에서 추출).

## 1. 무엇을 했나

`agent/src/nodes/parser.py`의 `split_clauses()`는 LLM 호출 없는 순수 규칙 함수라
이미 있는 6개 문서에 그대로 돌려서 조항 리스트를 뽑고, `data/labels.md`·
`data/real_labels.md`에 이미 존재하는 위치 기반 라벨("제2조 = 보증금 반환 지연" 등)을
그대로 매핑했다. 새로 만든 데이터는 없고, **문서 단위 라벨을 조항 단위로 풀어낸 것**.

| 문서 | 조항 수 | 위험 | 안전 |
|---|---|---|---|
| sample_lease_contract.txt | 5 | 4 | 1 |
| contract_02_finance_loan.txt | 7 | 6 | 1 |
| contract_03_lease_normal.txt | 7 | 0 | 7 |
| contract_04_gym_membership.txt | 7 | 4 | 3 |
| contract_05_molit_standard.txt | 16 | 0 | 16 |
| normal_deposit_terms.txt | 24 | 0 | 24 |
| **합계** | **66** | **14** | **52** |

**교수님이 "예금약관 24개조부터"라고 하신 게 정확히 여기서 가장 크게 기여** —
공정위 표준약관 원문이라 위험을 심지 않은 실물 데이터이고, 24개 "안전" 라벨을
검증 없이 그대로 얻는다.

## 2. 반드시 붙여야 하는 주의사항 (교수님 지적)

> "같은 문서 안 조항은 완전 독립 표본이 아니니 '독립 데이터 66개'라고 과장은 말 것"

같은 문서의 조항들은 다음 요인을 공유한다: 같은 원문 스타일/문체, 같은 파서 실행
1회의 부산물(조항 경계 오탐이 있으면 그 문서의 모든 조항에 영향). 다만
`agent/src/nodes/analysis.py:22`의 `_analyze_clause(clause_id, text)`가 조항마다
**개별 LLM 호출**로 판정하는 것을 확인했으므로, "판정 자체"는 조항 간 독립이다 —
공유되는 건 원문 스타일과 파서 경계뿐이라 우려는 완화되지만 완전히 사라지진 않는다.

**보고서에 쓸 문구(제안)**: "66개 조항 단위 평가 포인트를 확보했으나, 6개 원본 문서에서
파생되어 문서 간 독립성은 있지만 문서 내 조항 간 완전한 독립은 아니다. 통계 검정 시
문서를 클러스터 단위로 취급하는 것을 권장(예: 클러스터-강건 표준오차, 또는 최소한
문서 단위 층화)."

## 3. Train / Val / Test 분리안

교수님이 제시한 두 옵션(조항 단위로 쪼개서 나누기 / 5개 사례를 사례 단위로 나누기)을
검토한 결과, **아래 조합을 제안**한다 — 이유는 "이미 튜닝에 쓰인 데이터"와 "한 번도
안 쓰인 데이터"를 구분하는 게 두 옵션보다 더 근본적인 기준이기 때문이다.

### 3.1 핵심 원칙

지금 있는 9개 문서(자작 5 + real_labels 4)는 전부 **이미 프롬프트 v2 / 파서 v2 /
JUDGE_THRESHOLD=3.5 결정 과정에서 어떤 형태로든 눈으로 본 데이터**다
(`docs/context_ablation_2017-17.md`, `docs/eval_results_v2.md` 등 기존 실험 문서가
이 문서들로 파서·프롬프트를 반복 조정해왔다는 증거). 이제 와서 이 9개를 "test"라고
부르면 "시험 문제로 공부하고 그 문제로 시험 보는" 함정을 못 피한다.

→ **기존 9개 문서(66개 조항 포함) = Train/Val**, **새로 확보하는 데이터 = Test**로
나누는 게 가장 정직하다.

| 구분 | 구성 | 용도 | 손대는 방식 |
|---|---|---|---|
| **Train** | 기존 9개 문서 중 6개 (자작 3 + real_labels 3, 조항 단위로 풀면 약 45개) | 프롬프트 문구·rubric 앵커 예시·임계값 조정 | 자유롭게 반복 사용 |
| **Val** | 기존 9개 문서 중 나머지 3개 (약 21개 조항) | Train에서 만든 개선안 중 선택(예: persona prompt 여러 버전 중 채택) | 선택 단계에서만 사용, 반복 최적화 금지 |
| **Test** | **새로 확보하는 데이터** (AI Hub 승인분, LBox 필터링 판례에서 추출한 조항, 조정원 수동 검색 결과 등 — `docs/data_sourcing_research.md`) | 최종 보고 수치 산출 **1회만** | 파이프라인/프롬프트 설계 중 절대 열람 금지 |

### 3.2 기존 9개 문서의 Train/Val 6:3 분배(안)

문서 단위로 분배해야 "같은 문서 조항이 train과 val에 동시에 섞이는" 누수(leakage)를
막을 수 있다 — 조항 단위로 무작위 분배하면 같은 문서의 다른 조항이 train에 있고
val에도 있어서 val 성능이 부풀려진다.

| 문서 | 배정 | 근거 |
|---|---|---|
| sample_lease_contract.txt | Train | 초기 파서/프롬프트 개발에 가장 많이 쓰인 문서 |
| contract_02_finance_loan.txt | Train | 고위험 문서, 다양한 risk_type 학습에 필요 |
| contract_04_gym_membership.txt | Train | 임대차 외 도메인 일반화 확인용 (labels.md 명시 목적) |
| 광고대행 2025-03 (real_labels) | Train | |
| 신발도매 2013 (real_labels) | Train | |
| 즉시연금 2017-17 (real_labels) | Train | `docs/context_ablation_2017-17.md`에서 이미 집중 분석된 문서 — train이 맞음 |
| contract_03_lease_normal.txt | **Val** | 정상 대조군, false positive 확인용 |
| contract_05_molit_standard.txt | **Val** | 정부 공식 양식 정상 대조군 + Parser 강건성 테스트 겸용 |
| 즉시연금 2018-8 (real_labels) | **Val** | 교수님이 언급하신 "즉시연금 2018 + 정상 예금약관 집중" 조합과 일치 |
| normal_deposit_terms.txt (24조) | **Val** | 위와 동일 — 상동 |

이 분배는 교수님이 언급하신 두 가지 예시("표5 한 사례에 집중" / "즉시연금 2018+정상
예금약관에 집중") 중 **후자와 정확히 일치**한다 — 즉시연금 2018-8와 정상 예금약관을
Val(검증/선택 기준)로 쓰고, 나머지를 Train(튜닝 재료)으로 쓰는 구성.

### 3.3 "새 페르소나"(개선판) 검증 절차와의 연결

1. Train 6개 문서로 기존 Full/Baseline/w/o-persona 결과 중 좋은 프롬프트 요소를 뽑아 개선안 작성
2. Val 3개 문서(정상 예금약관 24조 + 즉시연금 2018-8 + 국토부 표준계약서)로 개선안이
   기존 대비 나은지 확인 — 여기서 **여러 개선 후보 중 하나를 고르는 것까지만** 허용
3. 확정된 최종 버전을 **Test(신규 확보 데이터)** 로 **1회** 실행해 보고서 수치로 확정

### 3.4 표본 수 현실 체크

Val이 3문서/21조항, Test는 아직 미확보 상태라 지금 당장 통계적 유의성을 논하긴
이르다. `docs/data_sourcing_research.md`의 AI Hub 신청·LBox 필터링을 통해 **Test를
최소 30건 이상 확보하는 것이 다음 단계의 실질적 병목**이다 — 우선순위 1번이 왜
"골드데이터셋 확보"인지와 직결.

## 4. eval.py 연동 (제안, 아직 미구현)

지금 `agent/eval.py`의 `EXPECTED_RISK_COUNTS`는 문서당 "위험 조항 개수"만 비교하는
근사치다(`eval.py` 상단 주석에 이미 "조항 단위 정답 매칭은 범위 밖"이라 명시돼 있음).
`data/clause_level_labels.csv`가 생겼으니 이제 **정확히 어느 조항이 위험으로
잡혔는지까지 대조하는 정밀 recall/precision**을 계산할 수 있다 — `clause_id`가
Parser 출력과 1:1 대응하므로 조인만 하면 됨. 다음 작업으로 제안하되, 지금 이
문서·CSV 자체는 eval.py 수정 없이도 바로 쓸 수 있는 상태.

## 5. 사람 평가 연동

`docs/human_llm_judge_agreement_design.md`의 표본 계층화(3.3절)에 이 조항 단위
데이터를 그대로 꽂을 수 있다 — 특히 "저점수 구간 확보" 요구사항을 위험 조항 14건
중심으로 채우면 된다. 다만 그 문서는 **파이프라인 최종 출력**(4-aspect 채점)을
평가 단위로 삼고, 이 문서는 **Parser 직후의 조항 자체**(위험/안전 이진 라벨)를
다루므로 서로 다른 층위의 데이터라는 점은 구분해둔다.
