# 검수 스프린트 3 — 통과 50행

> 절차는 `docs/collection_sprint2_lbox_candidates.md`와 동일하다: 제작 에이전트가
> 라벨을 제안하고, **제작자와 독립된 검수 에이전트 3개**가 원문을 재대조하며
> 반박을 시도한다. 2표 이상 기각이면 탈락시킨다.

## 실행 이력

| 회차 | 대상 | 결과 |
|---|---|---|
| 1차 | 문구 보유 후보 207건 | 승인 32 · 수정승인 1 · 기각 174 (생존율 16%) |
| 2차 | 후보 498건 (프롬프트 개선 후 전량 재검수) | 승인 47 · 수정승인 4 · 기각 359 (생존율 12%) |
| 3차 | 후보 564건 | **무효 — API 크레딧 소진** |

최종 반영: **50행** (내부 중복 제거 후). 골든셋 111 → **161행**.

## ⚠️ 3차 실행은 무효다

564건 중 **515건이 전부 `BadRequestError`(크레딧 소진)**였는데 로그에는 "기각"으로
기록됐다. 파이프라인이 실패를 승인으로 처리하지 않은 것은 맞지만, **API 이상과
진짜 기각을 구분하지 못해** 그 회차 로그가 통째로 오염됐다. 진짜 기각 사유 통계를
낼 수 없고, 재실행 시 무엇을 다시 봐야 하는지도 알 수 없다.

**그래서 3차 로그는 폐기하고 이 문서에 사실만 남긴다.** 후보 744건은 그대로
`data/staging/`에 있으므로, 크레딧 복구 후 검수만 다시 돌리면 된다.

### 재발 방지 (이미 반영)

- **사전 점검**: 대량 실행 전 호출 하나로 API 생존을 확인하고, 실패하면
  아무것도 기록하지 않고 중단한다.
- **회로 차단**: 연속 실패 5회면 즉시 중단하고 그때까지의 결과만 기록한다.
  `eval_repeat.CONSECUTIVE_FULL_FALLBACK_LIMIT`와 같은 사고방식이다.

## 2차까지의 기각 사유 분포

| 건수 | 사유 |
|---|---|
| 62+ | **조항 문언이 아니라 기관이 그 조항을 설명한 말** |
| 다수 | 조항 유·무효 판단 부재 (자료가 그 조항 자체를 판단하지 않음) |
| 4 | 축자 원문 부재 (제안이 원문과 불일치) |
| 49 | 기존 골든셋과 중복 (자동 기각) |

1위가 바뀐 것이 이번 스프린트의 발견이다. 심결문·판결문은 조항을 인용할 때
그것을 평가하는 문장과 뒤섞어 쓰는데, 설명문은 **원문 대조를 통과하므로**
축자 검증만으로는 걸러지지 않는다. 조항 판별을 따로 넣어야 했다.
