# Pairwise Judge 판사 패밀리 교차검증 — 1차 실행 분석 (2026-08-05)

## 배경

worker(Claude Haiku)가 만든 출력을 같은 Claude 패밀리 judge(Sonnet)가 채점하는 현재
구조는 self-preference bias(같은 패밀리 출력 과대평가, 문헌상 10~25% 수준) 가능성이
있다. 이를 통제하기 위해 `eval_pairwise.py`에 `--judge {claude,gemini}` 옵션을 추가해
**같은 44개 정답앵커 쌍을 두 패밀리 판사에게 독립적으로** 태웠다. 프로토콜: 쌍마다
debiased 비교(정/역방향 2회) × 3회 반복 → aspect별 다수결
(단발 채점 재현성 문제 통제, `docs/reproducibility.md` 참고).

이번 실행부터 judge 프롬프트 2종(`judge_rubric.txt`, `judge_pairwise_rubric.txt`)은
**rationale을 먼저 쓰고 점수/승자를 나중에 결정**하도록 수정된 버전을 사용했다
(점수 먼저 뱉고 근거를 끼워맞추는 생성 순서 문제 제거).

## 핵심 발견: 판사가 틀린 게 아니라 앵커 쌍 제작 결함이다

**서로 다른 패밀리의 두 판사가 같은 쌍에서, 반복해도 흔들리지 않고 같은 방향으로
"오답"을 선호**했다. 판사 편향이라면 패밀리마다 다르게 틀려야 하므로, 쌍 자체를
의심해야 한다. 해당 쌍을 열어보면 원인이 명확하다:

- hldcc_24 정답형 explanation: *"이 조항은 불명확한 수수료·이자 조건 문제가 있는
  것으로 판단됩니다. 포괄조항이 장기수선충당금까지 자동전가 못함(부분 무효) — 명시
  여부가 유효성 가름(대조: id=2358)"*

이건 사용자용 설명이 아니라 **라벨 파일의 판정 메모를 그대로 붙여넣은 것**이다.
(1) 페르소나 눈높이 문체가 아님 → clarity에서 밀리는 게 정당, (2) 조항 원문에 없는
외부 정보(민법 제379조, 조정위 판정, 내부 id 참조)를 인용 → 루브릭의 faithfulness
정의("원문에 없는 내용을 추가하지 않았는가")대로면 **오히려 정답형이 감점 대상**.
즉 판사들은 루브릭을 충실히 따랐고, 쌍이 설계 원칙을 어긴 것이다 —
`human_llm_judge_agreement_design.md` §11.2는 "두 출력 모두 톤·길이를 비슷하게 맞춰
판단 근거가 내용 정확성에서만 나오도록 통제"하라고 명시하고 있다.

**같은 패턴(정답형에 라벨 메모 템플릿 노출)이 44쌍 중 21쌍**에서 발견됐다 — 전부
PR#18에서 대량 추가된 확장분이다(수작업으로 만든 초기 10쌍은 해당 없음):

```
hldcc_37, hldcc_24, hldcc_2358, lbox_2488, lbox_90237_* (4건),
aihub_0193_* (5건), aihub_0190_* (3건), aihub_0079_* (5건)
```

Gemini의 오답/불안정이 몰린 쌍(hldcc_2358, lbox_116067, aihub_0190_명도이의금지,
aihub_0079_배액손해금 등)도 대부분 이 목록과 겹친다.

  템플릿 제거. gold 라벨·조항·오답형은 변경하지 않음.

  난도를 올리는 것을 검토.

## 후속 작업 (우선순위순)

1. **Anthropic 크레딧 충전 후 두 판사 모두 41쌍 재실행** — 1차 결과(위 표)는 결함
   데이터 기준이므로 재작성본으로 Claude·Gemini 둘 다 다시 돌려야 한다. 체크포인트가
   생겨 중단돼도 완료분은 보존된다. (기존 체크포인트/리포트는 판사별 파일이라
   재실행 전 체크포인트 jsonl만 삭제하고 실행할 것)
2. 재실행 후 두 패밀리 결과로 **판사 간 일치율(Cohen's κ)** 산출 — 사람 평가(RQ5)와
   대조할 LLM 쪽 기준선.
3. 사람 평가지는 반드시 **재작성본 41쌍**으로 제작 — 결함 쌍을 그대로 사람에게
   보여주면 RQ5(사람 선호-정답 일치율, manipulation check)도 같은 이유로 오염된다.
