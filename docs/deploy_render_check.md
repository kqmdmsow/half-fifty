# 배포: 콜드스타트 104초 + IP 403 확인 필요 (Render 대시보드)

데모 리허설 2차(통합 배포 상태 점검, 2026-08-23)에서 발견. 둘 다 애플리케이션
코드로는 재현 원인을 좁혔지만, 최종 확인·조치는 Render 대시보드 접근이 필요해
여기 기록만 남긴다.

## 1. 콜드스타트 104초 (agent는 22.6초)

- **실측**: backend 첫 요청 `/health` 104.0초, agent 첫 요청 22.6초. 두 번째
  요청부터는 둘 다 0.35초로 정상.
- `render.yaml`에는 이미 `plan: starter`로 설정돼 있다(무료 티어의 슬립 방지
  목적, 콜드스타트 방지 코멘트 포함). 문제는 **실제 Render 대시보드의 서비스가
  이 설정대로 배포돼 있는지 확인이 안 됨** — render.yaml은 blueprint 파일일
  뿐이고, 대시보드에서 수동으로 만들어진 서비스라면 반영 안 됐을 수 있다.
- 이 측정 직전에 #166(챗봇)·#167(로그인)이 머지·배포됐다 — 104초가 "이 배포
  직후 1회성 부팅 비용"(JPA/Security/Postgres 커넥션 풀 초기화 등)인지,
  아니면 "반복되는 슬립→웨이크 콜드스타트"인지 외부에서는 구분이 안 된다.
  로컬에서 JPA+Security+H2로 부팅 시간을 재보면 1.5초 수준이라, 원격
  Postgres 연결·네트워크 왕복이 실측치와 크게 차이나는 원인이라면 그 자체도
  살펴볼 값어치가 있다.

**확인해야 할 것**:
- (a) Render 대시보드에서 backend·agent 서비스가 실제로 `starter`(또는 그
  이상) 플랜인지, free 플랜으로 떠있는 건 아닌지
- (b) 104초가 매 배포 후 1회성인지, 일정 시간 유휴 후 재발하는지 (배포 없이
  15~30분 유휴 후 다시 요청해서 재현되는지 확인하면 구분됨)
- (c) 심사 기간(9/7~9/11)의 첫 접속이 이 상태라면 결격 리스크로 간주하고
  즉시 조치할 것

## 2. IP 403 차단 (rate-limit 테스트 후 광범위 발생)

- **재현**: `/api/contracts/learn-chat`에 21회 연속 요청(비용 상한 테스트,
  전부 인젝션 차단 문구라 LLM 호출 없음)을 보낸 뒤, 19번째 요청부터 403.
  그런데 이후 `learn-chat`의 **정상 질문**도 403, 전혀 건드린 적 없는
  `/api/auth/signup`도 403. `/health`만 계속 200.
- 앱 코드의 `LearnChatRateLimiter`는 `/api/contracts/learn-chat` 하나에만
  걸려 있고 `signup`과는 무관하다. 서로 다른 엔드포인트가 동시에 막히고
  `/health`만 살아있는 패턴은 **애플리케이션 rate limiter가 아니라 Render
  쪽 IP 레벨 보호(WAF/DDoS 방어 등)로 추정**된다.
- 9분 이상 모니터링했으나 세션 종료 시점까지 풀리지 않았다.
- 부수 관찰: rate limit이 걸린 시점이 앱 설정(시간당 20회)과 다른 19번째였고,
  응답도 앱이 던지는 429+메시지가 아니라 빈 바디의 403이었다 — 이것도 Render
  보호가 앱 코드보다 먼저 반응했다는 정황과 일치한다.

**확인해야 할 것**:
- (a) Render 프로젝트에 IP 차단·DDoS 보호·요청 속도 제한 설정이 있는지,
  있다면 임계값이 얼마인지
- (b) 일반적인 사용 패턴(느린 응답에 새로고침 여러 번, 버튼 여러 번 클릭
  등)으로도 이 보호가 유발될 수 있는지 — 심사위원이 이걸 맞으면 서비스가
  먹통으로 보여서 문제가 크다
- (c) 차단이 몇 분 만에 풀리는지, 얼마나 지속되는지
