# 설계 근거 정리 — 왜 이렇게 만들었나

발표·면접·리뷰에서 "왜?"에 답하기 위한 문서. 형식: **결정 → 이유 → 기각한
대안 → 증거**. (2026-08-11 기준, PR #24까지 반영)

---

## 1. 시스템 구조: 3-tier (React → Spring Boot → FastAPI)

**결정**: 프론트(5173) → 백엔드(8080, thin proxy) → 에이전트(8000, LangGraph).

**이유**:
- AI 로직은 Python 생태계(LangGraph·LangChain)가 표준이라 에이전트는 Python.
- 그 앞에 Spring Boot를 두는 건 ①팀 역할 분담(백엔드 전공 스택) ②인증·로깅·
  요청 검증 같은 서비스 관심사를 AI 로직과 분리하는 확장점 확보.
- 프론트가 에이전트를 직접 부르지 않게 해 AI 서버를 내부망에 격리할 수 있는
  구조(배포 시 보안 어필 포인트).

**기각한 대안**: FastAPI 단독(백엔드 역량 어필 불가, 서비스 관심사 혼입) /
Spring에서 LLM 직접 호출(Java LLM 생태계 미성숙).

---

## 2. 파이프라인: 왜 5단계 LangGraph인가

`Parser → Domain → Analysis → Persona → Judge (+재생성 루프 최대 2회)`

### Parser (모듈, LLM 아님)
- **왜 조항 단위로 쪼개나**: 판정의 근거 추적성. "이 계약서는 위험함"이 아니라
  "제5조가 이 문구 때문에 위험함"이어야 사용자가 행동할 수 있고, 평가도
  조항 단위 골든셋과 1:1로 맞물린다.
- **왜 LLM이 아닌가**: 조항 분리는 규칙으로 충분하고, 결정적(deterministic)
  이어야 같은 입력에 같은 조항 ID가 나와 평가·캐싱이 안정된다.

### Domain (PR #24 신규)
- **왜 필요한가**: 같은 문언도 문서 유형 따라 판정이 갈린다. "2기 연체 시
  해지"는 주택이면 민법 §640 표준(안전), 상가면 상임법 3기 보호 축소(위험).
  조항 단독으로는 **원리적으로** 구분 불가.
- **증거**: AI Hub 정독에서 나온 라벨 아티팩트 39건(짝 분리·조항 절단), 대조쌍
  실험 — 같은 조항이 도메인 주입만으로 주택→안전/상가→위험 분기 성공.
- **왜 문서당 1회인가**: 조항마다 판별하면 비용 n배 + 조항엔 지표가 없는 경우가
  대부분. 유형 지표(제목·당사자·목적 조항)는 문서 머리에 몰려 있다.
- **실패 안전**: 감지 실패 시 "알 수 없음" → Analysis가 기존(v2.1)과 동일하게
  동작. 새 단계가 파이프라인을 깨지 못하게 하는 폴백 설계.

### Analysis (핵심 판정)
- **왜 조항별 독립 호출인가**: ①오류 격리(한 조항 실패가 문서 전체를 안 망침)
  ②병렬화 가능 ③프롬프트 캐싱 히트(시스템 프롬프트 공유) ④평가 하네스가
  같은 함수를 재사용.
- **왜 JSON 강제 + 스키마 고정인가**: 프론트 렌더링과 평가 집계가 기계 판독
  가능해야 함. 4종 출력(설명/위험/근거/확인질문)은 착수보고서 <표 4> 그대로.
- **왜 10유형인가**: 처음 6유형은 가설이었고, 공정위 심결 1,046행 실측에서
  커버리지 52%로 구멍이 드러남 → 미탐 433건 전수 정독으로 신규 4유형 도출
  (66%로 +14pt). **유형 체계는 머리에서 나온 게 아니라 데이터에서 역산됨.**
- **왜 프롬프트에 '표준 조항 예외'와 '반격 가드'가 겹겹인가**: 탐지력을 올리는
  모든 변경은 오탐을 함께 올린다는 걸 반복 실측(v2→v2.1 회귀 4건). 가드는
  장식이 아니라 **각각이 실측된 오탐 사례 하나씩에 대응**한다.

### Persona (표현 적응)
- **왜 판정과 분리했나**: "무엇이 위험한가"(사실)와 "어떻게 설명하나"(표현)는
  독립. 분리하면 고령층·외국인 등 페르소나를 추가해도 판정 로직 재검증이
  불필요 — 다국어 확장(예정)이 싸지는 이유.

### Judge (품질 게이트)
- **왜 있나**: LLM 출력은 확률적이라 가끔 저품질이 나온다. 4 aspect(이해용이성/
  충실성/위험식별/행동지침) 채점으로 미달 출력을 걸러 **최대 2회 재생성** —
  사용자에게 나쁜 출력이 나가는 빈도를 구조적으로 낮춤.
- **왜 worker(Haiku)와 judge(Sonnet)를 다른 모델로**: 채점자가 생성자보다
  강해야 채점이 의미 있고, self-preference(자기 출력 선호) 완화.
- **왜 rationale을 점수보다 먼저 쓰게 하나**: 점수 먼저 뱉으면 근거를 점수에
  꿰맞춤(사후 합리화). 근거 선행 강제가 채점 일관성을 올린다는 게 LLM-as-judge
  문헌의 표준 권고.
- **왜 pairwise는 A/B를 뒤집어 2번 재나**: 위치 편향(먼저 온 답 선호) 상쇄.
- **재생성 한도가 2회인 이유**: 비용 상한. 2회로 안 되면 needs_review 플래그로
  정직하게 실패를 노출(무한 루프·조용한 실패 방지).

## 3. Judge를 "끝내도 된다"고 판단한 기준

Judge는 저울이다. 저울 정밀도의 목적은 **결정(프롬프트 A vs B)이 노이즈로
뒤집히지 않는 것** — 그 이상은 낭비.

통과시킨 기준 3개:
1. **판사 독립성**: 4개 모델 패밀리가 앵커쌍 42개에서 97~100% 합의 —
   단일 모델 편향이 결론을 못 바꿈.
2. **정답 있는 문제의 정확도**: 앵커쌍에서 순서 뒤집기 후에도 정답 방향 유지.
3. **잔여 불일치의 설명 가능성**: Solar 엄격성은 문서화된 개성(랜덤 오차 아님).

**남은 마지막 조각 = 사람 평가와의 상관** (외부 평가자 채점 → Gwet's AC1).
지금까지는 "LLM끼리의 합의", 사람 상관까지 확인돼야 완전 종결.

**다시 여는 조건**: 루브릭 대폭 변경 / 새 도메인에서 aspect 부적합 /
사람 상관 낮음. 이 셋 외에는 재측정 금지(비용 통제 합의, 2026-08-08).

## 4. 평가 체계: 왜 이렇게 복잡한가

- **train/val/test 분리 + Test 1회 원칙**: test를 보며 튜닝하면 성능이 아니라
  암기를 측정하게 됨(오염). train/val은 자유 반복, Test 40은 개선 확정 시
  1회만. 같은 사건의 조항은 같은 split(누수 방지).
- **골든셋의 라벨 등급(A/C)**: A=정부·법원이 실제 무효/유효 판정한 조항,
  C=AI Hub 자체 판단. "정확도 X%"를 주장할 땐 A등급만 뗀 수치를 쓴다 —
  근거의 강도를 수치의 강도와 일치시키기 위함.
- **왜 무료 모델(Solar)로 대량 측정하나**: 크레딧 사고 2회 후 합의 — 대량
  실행은 무료, 제품 워커(Haiku) 확정 측정은 소량만. 단, **Solar 30행 평가는
  일간 변동이 커서(같은 프롬프트가 X 8~12) 미세 튜닝의 저울로 쓰면 안 됨**
  (2026-08-11 실측). 상대 비교 + 3회 반복 다수결로만 사용.
- **폴백 은폐 사고와 fail-fast**: `_analyze_clause`의 폴백(주의/해당 없음)이
  크레딧 소진 400 오류를 정상 결과처럼 위장 → 4,115건 오염 사고. 이후 평가
  하네스는 invoke_json 직접 호출 + 크레딧·인증 오류 즉시 전체 중단 +
  체크포인트(JSONL) 재개. **제품의 우아한 실패와 평가의 시끄러운 실패는
  반대 방향이 옳다.**
- **왜 앵커쌍인가**: judge를 검증하려면 "정답이 있는 채점 문제"가 필요.
  품질 차이가 명백하도록 설계한 쌍 42개가 judge의 단위시험 역할.

## 5. 데이터: 왜 이 소스, 이 절차인가

- **수집 3단 파이프라인** (키워드 필터 → 원문 정독 → 독립 적대적 검수):
  검수자를 수집자와 분리해 확증 편향 차단. 검수 통과율이 100%가 아니었다는 것
  자체가 파이프라인이 작동한다는 증거(기각 사례: 19014 라벨 충돌).
- **축자 인용 + 기관 판단 필수**: "위험해 보이는" 조항이 아니라 "기관이 위험을
  판정한" 조항만 라벨링 — 우리의 감이 아니라 공적 판정이 정답지.
- **경계 안전 사례 최우선**: "위험해 보이나 유효"(§565 해약금 등) 사례가
  오탐 억제의 핵심 재료. 위험 사례만 모으면 과잉 경고 모델이 된다.
- **AI Hub 원본은 git 밖**: 이용정책상 제3자 열람·제공 금지 + 국외 반출 합의
  필요 → public 레포 게시 불가. 접근 절차는 docs/aihub580_data_access.md.

## 6. 비용·신뢰성 장치

- **프롬프트 캐싱**: 시스템 프롬프트(유형 기준+가드, ~4k 토큰)가 조항마다
  반복되므로 cache_control로 히트 — Sonnet에서 2,162토큰 히트 실측.
- **병렬화(ThreadPoolExecutor)**: 조항별 독립 호출이라 안전하게 병렬 가능.
- **체크포인트 재개**: 대량 실행은 중단이 기본값이라는 전제(크레딧·레이트리밋)
  로 설계. 재실행 시 이어서.
- **429 백오프 vs 400 즉중단 구분**: 일시 오류는 기다리면 되고, 크레딧·인증
  오류는 기다려도 안 되므로 전체 중단이 데이터 오염보다 낫다.
